## 3. 问题修复清单（现象 → 根因 → 修复 → 验证）

以下每个问题都在本机复现、修复并验证过（部分提供复现截图）。

### R1 启动器 bat 乱码报错
- **现象**：双击 bat 报 `'JRE' 不是内部或外部命令…`、`'-cp' 不是…`。
- **根因**：bat 以 UTF-8 保存且含中文；中文 Windows 的 cmd 按 GBK 解析批处理，中文字节被拆错行。
- **修复**：所有 bat 改为**纯 ASCII**（注释与命令均英文），中文只出现在文件名上（文件名不影响 cmd 解析）。
- **验证**：校验字节 0 个非 ASCII；双击可正常启动/生成诊断报告。

### R2 点关闭关不掉 / 界面 AppHang（Windows 事件日志 AppHangB1）
- **现象**：引擎加载期间点 × 无反应，窗口最终被系统判定"无响应"。
- **根因**：`windowClosing` 在 EDT 同步执行全部清理（存档→写配置→杀引擎→杀辅助进程→`System.exit`），
  任一步被引擎线程阻塞，窗口就永不关闭；另有辅助 JVM 残留。
- **修复**（`LizzieFrame.java` windowClosing）：立即隐藏所有窗口 → 清理放入守护线程 →
  **5 秒看门狗强制 `System.exit(0)`**；并注册 JVM 关闭钩子强制结束时钟辅助进程。
- **验证**：加载中关闭 1 秒退出、加载完成后 0.5 秒退出；退出后 `javaw`/辅助进程零残留。

### R3 加载阶段注释区显示原始引擎日志
- **根因**：`setComment()` 在引擎未加载时把 GTP 控制台文本（原始 stderr）塞进注释区。
- **修复**：改为显示"引擎正在加载中… 请等待引擎加载完毕"。

### R4 官方默认"手动选择引擎"
- **现象**：每次启动弹"选择要加载的引擎"对话框。
- **修复**：`config.txt` 置 `autoload-default: true`，启动自动加载默认引擎。

### R5 ★ 背景变黑 / 工具栏图标全部空白（核心问题）
- **现象**：两侧面板纯黑、工具栏图标空白、棋盘失去木纹，但文字与棋盘网格正常。
- **诊断证据**（用户机器 `诊断结果.txt`）：
  ```
  theme/background.jpg : 读取异常 javax.imageio.IIOException: Can't create cache file!
  jar内 assets/open.png : 异常 javax.imageio.IIOException: Can't create cache file!
  ```
- **根因**：Java 的 ImageIO 默认把解码数据缓存到系统临时目录；该机器 TEMP 不可用（磁盘满/权限/
  安全软件），导致**所有图片解码失败**——图标（ImageIcon）空白、主题背景缺失（黑）、棋盘退化为纯色。
  用官方原版 jar + TEMP 指向不存在的路径可 100% 复现该画面。
- **修复**：`Lizzie.main` 启动时 `ImageIO.setUseCache(false)`（纯内存解码，不再依赖 TEMP）；
  另在 `BoardRenderer.getWallpaper()` 增加 null 兜底、`drawContainer()` 越界/异常时补底色不再留黑。
- **验证**：同样"TEMP 损坏"环境下，修复版面板恢复主题灰、图标全部显示（官方版为纯黑+空白）。

### R6 ★ 选点圆圈（候选点）不显示（核心问题）
- **现象**：分析正常运行、右侧候选列表有数据，但棋盘上的候选圆圈与胜率数字不出现。
- **诊断证据**（stderr）：
  ```
  java.io.IOException: Problem reading font data.     ← Font.createFont 失败（同样依赖 TEMP）
    at featurecat.lizzie.util.Utils.loadFonts(Utils.java:91)
  Exception in thread "AWT-EventQueue-0" java.lang.NullPointerException:
    Cannot invoke "java.awt.Font.deriveFont(int, float)" because "fontBase" is null
    at BoardRenderer.makeFont → drawStringForOrder → drawOrder → drawLeelazSuggestions
  ```
- **根因**：自定义字体 `OpenSans-Semibold.ttf` 通过 `Font.createFont` 加载（Windows 下需临时文件），
  TEMP 不可用时抛异常，`winrateFont` 保持 null；绘制候选点（圆圈+数字）时 `makeFont` 抛 NPE，
  整层选点绘制中断。
- **修复**：
  1. `Utils.loadFonts()`：先用系统字体（SansSerif）兜底，`createFont` 失败不再留 null；
  2. `BoardRenderer.makeFont()`：null 字体兜底；
  3. `Lizzie.main` 新增 `ensureUsableTempDir()`：启动时检测并自动回退到可用临时目录（程序目录 `temp\`、
     `%LOCALAPPDATA%\Temp`、`%USERPROFILE%\Temp`、`%SystemRoot%\Temp`），使字体/JCEF 等也能正常工作。
- **验证**："TEMP 损坏"环境下选点圆圈正常出现（绿色/青色圆圈+胜率数字），与正常环境一致。

### R10 选点（候选圆圈）完全不显示
- **现象**：右侧候选列表有数据、引擎在分析，但棋盘上没有任何候选圆圈/胜率数字。
- **根因**：BoardRenderer.isShowingRawBoard() 把「分支长度 == 0」也当成"纯棋盘"模式
  （displayedBranchLength == SHOW_RAW_BOARD || displayedBranchLength == 0）。
  分支长度在某些操作下（滚轮调整分支/变化图为空时 incrementDisplayedBranchLength
  会把长度置 0）变成 0 后，整个选点绘制分支被跳过，且重启前不会恢复。
- **修复**：isShowingRawBoard() 只认显式的 SHOW_RAW_BOARD(-1)，分支长度 0 视为
  "不画变化图"的正常状态（BoardRenderer.java 与 FloatBoardRenderer.java 同步修复）。
- **附加**：加入带开关的诊断日志（-Dlizzie.debug.suggestion=true 时写
  suggestion-debug.txt，记录 branchLen/rawBoard/候选开关/数据量/分支状态等），
  并提供 工具\启动并记录日志.bat 便于定位同类问题。
### R7 渲染管线 / 高 DPI 兼容
- 主 exe 增加 `-Dsun.java2d.d3d=false`；兼容模式 exe/bat 额外加 `-Dsun.java2d.noddraw=true`
  与 `-Dsun.java2d.uiScale=1.0`（高 DPI 缩放会导致工具栏按钮/图标布局异常）。

### R8 诊断工具
- `工具\诊断.bat` + `diag.jar`：检查程序文件与哈希、Java/OS 版本、屏幕分辨率与缩放、
  **TEMP 目录可写性与临时文件创建测试**、以及图片（主题/图标）**开/关缓存两种模式**的解码结果，
  输出 `诊断结果.txt`。上两轮问题（R5/R6）就是靠它精确定位的。

## 4. 「形势判断」统计方式（当前实现）

### 4.1 触发与整体流程

```
菜单/底部工具栏「Kata评估」或「形势判断」
   → Lizzie.frame.toggleShowKataEstimate() / clearKataEstimate()
   → 独立形势判断引擎 KataEstimate（进程独立于主分析引擎）
        · 启动命令 = config.txt 的 estimate-command
        · 启动后按模式发送 kata-set-rules chinese（数子/Area）或 japanese（数目/Territory）
        · 每步：clear_board → boardsize → 逐手 play 同步当前棋谱（KataEstimate.syncboradstat, :542-560）
        · 然后发送 kata-raw-nn 0（纯网络评估，无搜索）（KataEstimate.countStones, :584-602）
   → 解析 whiteOwnership 逐点值 → 阈值化 → 死子/真目判定 → 统计 → 界面显示
```

相关代码：`KataEstimate.java`（引擎驱动与统计，639 行）、`EstimateResults.java`（结果面板）、
`BoardRenderer.drawEstimateImage/drawKataEstimateBySize/drawKataEstimateByTransparent`（棋盘着色）、
`LizzieFrame.drawKataEstimate`（入口）。

### 4.2 数据来源：`kata-raw-nn 0` 的 `whiteOwnership`

- 命令：`kata-raw-nn 0`（固定对称 0，即时返回，无 MCTS 搜索）。
- 输出块 `whiteOwnership` 后紧跟 19 行、每行 19 个数值，范围 -1..1：
  **正值表示该点偏向白方控制，负值偏向黑方**。
- 读取代码（`KataEstimate.parseLine`, :262-289）：
  ```java
  Double temp = -Double.parseDouble(params[i]);      // 取反 → 黑为正
  if (temp >= 0.4 || temp <= -0.4) tempcount.add(temp);
  else tempcount.add(0.0);                            // |v|<0.4 视为中性（单官/未定）
  ```
  其中 0.4 即 `estimateThreshold`（`Config.java:74` 默认 0.4，可在设置里改 `estimate-threshold`）。
- 整个棋盘 19×19=361 个点收集齐后调用 `territory()` 做统计（:373-472）。

### 4.3 逐点处理规则（`territory()`）

对棋盘每个交叉点（黑为正、白为负的 `count`）：

| 点上的内容 | 判定 | 计数 |
|---|---|---|
| 黑子且 count < 0 | 该黑子为**死子** | `blackPrisonerCount++`（黑方被提）且 `whitepoint++`（计入白空） |
| 黑子且 count ≥ 0 | 活棋 | `blackAlive++`；若 count>0，显示值归 0 |
| 白子且 count > 0 | 该白子为**死子** | `whitePrisonerCount++` 且 `blackpoint++` |
| 白子且 count ≤ 0 | 活棋 | `whiteAlive++`；若 count<0，显示值归 0 |
| 空点且 count > 0 | 黑控制点；再判断**四邻是否同号**（`getRealCountBlack`, :345-371） | 四邻全部 >0 才算**真目** → `blackpoint++`；否则按 0 处理 |
| 空点且 count < 0 | 白控制点；四邻全部 <0 才算**真目**（`getRealCountWhite`, :317-343） | → `whitepoint++` |

> 说明：死子会自动转为对方的目（围棋点目常识）；四邻校验用于剔除"渗透/单点高值但周围不属于同方"的伪目，
> 使点目结果更接近真实终局。

### 4.4 统计公式（`EstimateResults.Counts`, :264-301）

设：
- `blackpoint` / `whitepoint`：双方**目数**（真目 + 死子转化来的目）
- `blackEatCount` / `whiteEatCount`：对局中**已提子数**（来自棋盘数据）
- `blackPrisonerCount` / `whitePrisonerCount`：局面中被判**死子数**（本方死子）
- `blackAlive` / `whiteAlive`：双方**活子数**
- `blackCaptured = blackPrisonerCount + whiteEatCount`，`whiteCaptured = whitePrisonerCount + blackEatCount`

两种统计模式（`estimateArea`，默认 false）：

| 模式 | 黑 | 白 |
|---|---|---|
| **数目模式（Territory，默认）** | `allBlackCounts = blackPoints + blackEatCount + whitePrisonerCount` | `allWhiteCounts = whitePoints + whiteEatCount + blackPrisonerCount` |
| **数子模式（Area）** | `allBlackAreas = blackAlive + blackPoints` | `allWhiteAreas = whiteAlive + whitePoints` |

领先目数（面板显示）：
```
lead = |allBlackAreas - allWhiteAreas|
显示值 = lead / 2.0        // 面积差换算成目差（一点=半目）
```
（`EstimateResults.java:340` 与 paint 中 `lead / 2.0`）

> 因此"形势判断"给出的不是胜率，而是**基于神经网络逐点归属的目数/子数统计**：
> 数目模式 ≈ 终局目数（含提子与死子），数子模式 ≈ 中国规则数子（活子+空）。
> 面板同时列出双方"提子/死子/目数/总和"，并给出当前领先方与领先目数。

### 4.5 界面呈现

- **结果面板**（`EstimateResults`）：标题「形势判断」（`EstimateResults.title`），按钮：
  判断形势 / 自动判断（循环，`isAutocounting`）/ 数目模式↔数子模式切换 / 关闭判断；
  显示黑方/白方的提子、死子、目数、总和与领先目数。
- **棋盘着色分两条路径**：
  1. **独立形势判断引擎路径**（本文 §4.1~4.4，`kata-raw-nn 0` + `KataEstimate.territory()`）：
     通过 `BoardRenderer.drawEstimateImage` 逐点画 **1/2 格大小的黑白小方块**
     （黑=黑方归属、白=白方归属；活子/死子位置归 0 不标）。
  2. **主引擎热力图 ownership 路径**（`drawKataEstimate`，`LizzieFrame.java:9521-9560`）：
     若开启 `show-katago-estimate-by-size`（纯点目按大小）→ `drawKataEstimateBySize`
     画不同直径圆点；否则 `drawKataEstimateByTransparent` 整片半透明着色。
- **自动判断**：开启后每落一手自动重新估算；若 5 秒内无结果，按全 0 显示避免卡住
  （`KataEstimate.countStones`, :606-630）。
- 可同时显示在主棋盘与副棋盘（`show-katago-estimate-onmainboard / -onsubbord`）。

### 4.6 与主引擎分析的关系

| | 主分析（kata-analyze） | 形势判断（kata-raw-nn 0） |
|---|---|---|
| 引擎 | 主引擎（默认 b11c768-tf3） | 独立形势判断引擎（b10c384-tf2） |
| 方法 | MCTS 搜索（数千~数万访问） | **纯神经网络一次前向**，无搜索 |
| 输出 | 胜率/目差/候选点/PV | 每个交叉点的归属值 → 点目统计 |
| 速度 | 3~5 次/秒（b11c768，核显） | 数秒内出结果（模型小、无搜索） |
| 用途 | 选点、变化图、胜率曲线 | 终局点目、死活判断、形势总览 |

两者互不干扰：形势判断引擎与主引擎是两个独立进程，棋盘状态由主程序同步（play 重放当前棋谱）。

### 4.7 当前形势判断配置

- `config.txt` → `estimate-command`：

### 4.8 已知限制

1. 形势判断是"神经网络直觉"水平：`kata-raw-nn 0` 不做搜索，未定形/劫争/大混战局面误差较大；

## 9. 形势判断统计增强：按「第一选点目差」校准（本轮新增）

### 9.1 计算方案

1. **取目标目差**：主引擎分析结果第一选点（estMoves[0].scoreMean，即 KataGo 的
   scoreLead，当前行棋方视角、含贴目）→ 转成黑方视角 leadBlack
   （黑方行棋取正、白方行棋取反）→ **四舍五入**得到目标目差 	argetLead。
2. **取归属图**：形势判断引擎（b10c384-tf2）kata-raw-nn 0 的 whiteOwnership
   逐点值取反得到"黑为正"的归属值  ∈ [-1,1]。
3. **分类（阈值可配置，默认 低=0.2、高=0.5）**：
   - **有己方棋子的点：不计入己方目数、也不显示为己方领地**（统计口径从“面积”改为“空”）；对方死子仍计入并显示为提子方领地；
   - 空点 |v| >= 高阈值(0.6)：直接计 1 目；空点 低阈值(0.4) <= |v| < 高阈值(0.6)：按 |v| 从大到小排序后逐个计入；
   - |v| < 低阈值(0.4)：视为单官/未定，忽略。
4. **统计**：先由强归属点得到基础差 aseDiff = 黑点数 − 白点数；
   再把不确定点按 |v| 降序**逐个计入**（每个点给所属方 +1 目），
   每加入一个点后检查累计差值：**一旦等于目标差值就停止**，剩余不确定点不再计入。
5. **目标差值换算**：统计口径是空（不含己方棋子），而 scoreLead 对应面积差（含棋子），故先换算面积目标 `targetArea = round(lead + 贴目)`，再换算空目标 `targetTerritory = targetArea − (黑活子 − 白活子)`；
   	argetArea = round(targetLead + 贴目)；若把 estimate-calibrate-include-komi
   设为 false 则直接用 	argetLead 与目数差比较。
6. **输出**：
   - 最终归属图（强归属点 + 已纳入的不确定点，未纳入点为 0）→ 棋盘小方块着色；
   - 统计：黑点 B、白点 W、面积差 diff、目标 targetArea、停止原因
     （EXACT 精确命中 / BASE 基础点已等于目标 / EXHAUSTED 不确定点用尽仍未达标 /
     NO_DATA 无数据）→ 结果面板"形势判断"显示；
   - 详细记录写入包目录 estimate-calibrate.txt（便于核对）。

| estimate-high-threshold | 0.6 | 高阈值：|归属|>=此值 直接计 1 目（对话框新增输入框） |
| estimate-low-threshold |  .4 | 低阈值：低于此值忽略；介于两阈值之间按强度排序计入 |
| estimate-calibrate-include-komi | 	rue | 目标差值是否加贴目换算（true=面积差口径） |

### 9.4 验证结果

1. **合成用例（5/5 通过）**：精确命中、用尽、基础点即命中、阈值变化、不含贴目模式。

### 9.5 使用提示

- 该统计在「形势判断 → 自动判断」（使用独立形势判断引擎 b10c384 的路径）下生效；
  普通「判断形势」（主引擎 raw-nn）仍走原逻辑。
- 开局/稀疏局面归属值普遍低于 0.4，可能得到 EXHAUSTED（黑/白 0 目）——这是正常结果，
  中后盘归属明确后才会出现"按目差分档统计"的效果。
- 想调节松紧：把小阈值调低（0.3）会纳入更多边缘点；调高（0.5）只保留更强的归属点。

### 9.6 阈值到底怎么设置（与设置对话框的关系）

- 设置对话框「KataGo阈值」→ config.txt 的 **estimate-threshold**（当前 0.5），在算法中作为**低阈值**：
  |归属| 低于它的点视为单官/未定，不参与统计。
- 高阈值来自 config.txt 的 **estimate-high-threshold**（默认 0.5），并已在「设置形势判断引擎」对话框新增**高阈值输入框**：|归属| >= 高阈值 直接计 1 目。
- 介于两者之间的点：按 |归属| 从大到小排序，逐个计入直到累计目差 = 第一选点目差（四舍五入）即停止。
- 若 estimate-high-threshold 设得比低阈值还小，程序会自动把高阈值修正为低阈值 + 0.05。
- estimate-calibrate = false 时退回旧的单阈值粗筛（就是设置对话框注释所说的"粗略的按阈值划分"）。
- 调大低阈值 = 更严格（只承认更确定的归属，容易出现 EXHAUSTED、结果偏小）；调小 = 更宽松。

### 9.7 口径更新：目数=空（本版）

- **有己方棋子的点位**：不统计进己方目数，也**不在棋盘上显示**为己方领地 → 统计结果就是己方的“空”。
- **对方死子**：仍计入并显示为提子方的领地（等同数目规则中提子后的目）。
- **目标换算**：面积目标 `targetArea = round(第一选点目差 + 贴目)`；
  空目标 `targetTerritory = targetArea − (黑活子数 − 白活子数)`（因为 面积 = 活子 + 空）。
- **面板映射**：
  - 数目模式：黑 = 空 + 黑提子；白 = 空 + 白提子（死子已含在空计数中）；
  - 数子模式：黑 = 活子 + 空 = 实际面积；白同理。
- **验证**：新增合成用例 F（10 颗黑活子 + 5 颗黑方地域内白死子 + 10 个黑空点 + 5 个白空点，
  目差 12.5、贴目 7.5）：`stop=BASE B=15 W=5 diff=10 alive=10/0 targetArea=20 targetTerritory=10` ✅

### 10.3 进一步的资源优化（本版）

- **归属图哈希去重**：`drawEstimateImage` 先计算地图哈希，与上次相同则直接返回，不重新分配/绘制图像
  （形势判断重复触发时几乎零开销）。
- **空口径减小图像绘制量**：己方棋子点不再绘制，着色方块数量减少。
- **内存**：归属图缓冲复用 + 地图哈希去重，避免每次估计产生 ~3MB 临时图像与 GC 压力。
- **CPU**：同一局面不重复请求 raw-nn；引擎 info 刷新与形势判断都只重绘主面板；字体派生缓存。

## 16. 形势判断统计修正：空 / 死子 / 提子（本版）

### 16.1 修正内容

**问题 1**：己方棋子被当作己方领地显示/统计。
**修复**：
- 统计层：己方活子点**既不计入目数，也不进入归属图**（map=0），不会显示；
- 显示层：`drawEstimateImage` 增加安全检查，即使是旧数据也**绝不把己方棋子点画成己方领地**。

**问题 2**：己方领地内的对方死子被标记成己方领地，但没有单独计入死子、也没有加到最终结果。
**修复**：统计拆分为三项并分别返回：

| 项 | 含义 | 面板显示 |
|---|---|---|
| `blackEmpty` / `whiteEmpty` | **空**（只有空点，不含任何棋子） | 领地 |
| `blackDeadEnemy` | 黑方区域内的**白死子**数（反之亦然） | 死子 |
| 提子数 | 对局中实际提掉的棋子（`blackCaptures`/`whiteCaptures`） | 并入差值 |

最终结果按用户要求计算：

```
差值(黑) = 空 + 对方死子 + 提子
差值(白) = 空 + 对方死子 + 提子
盘面领先 = 黑差值 - 白差值
```

**目标换算同步调整**（统计的是空，而选点目差是面积口径）：

```
targetArea  = round(第一选点目差 + 贴目)
targetEmpty = targetArea - (黑活子 - 白活子) - (白死子 - 黑死子)
```

### 16.2 校准日志新增字段

`estimate-calibrate.txt` 现在会输出：
`blackEmpty / whiteEmpty / deadWhite / deadBlack / blackAlive / whiteAlive / targetEmpty` 等，便于核对。

### 16.3 验证

- 合成用例 7/7 通过，其中：
  - F（贴目口径/死子）: `stop=BASE B=15 W=5 diff=5 alive=10/0 targetArea=20 targetEmpty=5`
  - G（白方区域内黑死子）: `B(empty)=3 W(empty)=6 deadBlack=4 alive=0/8 targetArea=7 targetEmpty=19 stop=EXHAUSTED`
- 程序启动冒烟测试正常（无 stderr 错误）。

### 16.4 棋子索引对齐修复（重要）

- **根因**：`Board` 的 stones 数组是**列优先**（`index = x * height + y`），而形势判断的归属图
  （`kata-raw-nn 0` 的 whiteOwnership）是**行优先**（`index = y * width + x`）。
  之前直接按下标对齐 → 棋子颜色与归属错位：
  - 己方活子被当成空点/对方死子（导致"己方棋子被算成己方目"、"死子数虚高"）；
  - 归属图还会把己方棋子画成己方领地。
- **修复**：用 `Board.getCoord(i)` 把 stones 的下标转成 (x, y)，再换算成行优先下标
  `x + y * width` 后写入 stoneColors / 过滤表（`KataEstimate` 与 `BoardRenderer` 两处同步修）。
- 影响：死子数、空点数恢复正确；己方棋子不会再显示为己方领地。

## 17. 盘面领先改为“面积差”口径（本版）

### 17.1 问题

面板“盘面领先”之前用的是 **差值(空+死子+提子)之差**，即纯“空”的差，
没有把双方棋子数（面积）算进去。示例局面：

- 空：黑 43 / 白 63（白空多 20）
- 但黑活子比白多很多（面积差约为 +7）
- 旧显示：白领先 19 目（实际是空差）
- 正确：黑盘面领先约 7 目（面积差）

### 17.2 修正

校准模式下，盘面领先改为按 **面积** 计算：

```
面积(黑) = 黑活子 + 黑空 + 白死子（黑方区域内的对方死子）
面积(白) = 白活子 + 白空 + 黑死子
盘面领先 = |面积(黑) - 面积(白)|（不含贴目）
```

面板三行保持：

| 行 | 含义 |
|---|---|
| 领地 | 空（只数空点） |
| 死子 | 己方区域内的对方死子 |
| 差值 | 空 + 对方死子 + 提子 |

由于校准算法最终会让面积差 ≈ `round(选点目差 + 贴目)`，盘面领先应与引擎评分一致
（例如引擎分数 -0.8、贴目 7.5 → 面积差约 7 目）。

### 17.3 显示实现

- `EstimateResults` 新增 `calibratedAreaBlack/White`（活子+空+对方死子）；
- 校准模式下走独立的 `paintCalibrated()`：盘面领先按面积差绘制，领地/死子/差值分别显示。

## 18. 阈值默认值调整（本版）

按实测效果把高低阈值的默认值改为：

```
低阈值 estimate-threshold      = 0.2
高阈值 estimate-high-threshold = 0.5
```

原因：高低阈值差距太小时（如 0.4/0.6），介于两者之间的“不确定点”数量不足，
校准统计容易提前用尽或大幅偏离目标；放宽到 0.2~0.5 后：
- 低阈值 0.2：更多边缘点纳入候选；
- 高阈值 0.5：强归属点门槛降低，基础统计更充分；
- 中间段 0.2~0.5 有足够的点用于“按目差逐个计入”，结果更接近引擎评分。

设置对话框里仍可随时修改这两个值（「KataGo阈值」= 低阈值，「高阈值」= 高阈值）。
