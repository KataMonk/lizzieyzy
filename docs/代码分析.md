## 2. 总体架构与数据流

```
main() [Lizzie.java]
  └─ Config (config.txt / persist.txt / save\saveBoardConfig.txt)
  └─ LizzieFrame + BoardRenderer + GtpConsolePane (Swing 主界面)
  └─ EngineManager (analysis 包)
       └─ Leelaz ×N  ── stdin/stdout ── GTP 引擎子进程（本地 ProcessBuilder 或 SSH）
       ├─ AnalysisEngine   ── KataGo "kata analyze" JSON 模式（闪电/批量分析）
       ├─ KataEstimate     ── kata-raw-nn / Zen territory（形势判断）
       ├─ ContributeEngine ── katagotraining.org 分布式训练
       └─ ReadBoard / GetFoxRequest / CaptureTsumeGo ── 外部捆绑程序桥
  └─ Board (rules 包) ── BoardHistoryList 双向链表 ── SGFParser 读写棋谱
```

- **引擎分析数据流**：`EngineManager` 构造时按配置为每个引擎创建 `Leelaz` 并按需预启动 → `Leelaz.startEngine()` 启动进程并发 `name/version/list_commands` → 按 `name` 响应识别引擎类型 → `ponder()` 发 `kata-analyze`/`lz-analyze` → `read()` 线程逐行解析 `info` 行为 `MoveData` → 写入 `BoardData.tryToSetBestMoves` → `LizzieFrame.refresh()` 渲染选点/胜率/PV。
- **包间依赖方向**：`gui` ⇄ `analysis`（通过 `Lizzie.leelaz`、`Lizzie.engineManager` 等全局单例互相调用）；`analysis` → `rules` 单向写棋盘；`rules` 不反向依赖 `analysis`。全局状态集中在 `Lizzie` 类的 static 字段（`Lizzie.java:35-54`）。

## 3. 各部分功能

### 3.1 根包（`featurecat.lizzie`）

- **`Lizzie.java`（450 行）**：入口与全局单例容器（`config/frame/board/leelaz/leelaz2/engineManager` 等）。启动流程：初始化日志重定向（可选写 `LastConsoleLogs_*.txt`）→ 检测 Java 版本与系统缩放 → 首次使用向导（换主机名/首次运行则重置提示与配置）→ 按语言加载 `l10n` 资源包 → 设置字体与 LookAndFeel → 按配置自动加载引擎（默认/上次/空）或弹出 `LoadEngine` 引擎选择框 → `start()` 创建主窗口、GTP 控制台、`EngineManager`，并按配置预启动形势判断引擎 `KataEstimate` 与闪电分析引擎 `AnalysisEngine`。退出时 `shutdown()` 保存配置、杀掉全部引擎进程。**注意**：自动检查更新逻辑整段被注释（`Lizzie.java:272-278`），版本检查功能已停用。
- **`Config.java`（2556 行）**：三份 JSON 配置的加载/合并/保存——`config.txt`（`config/leelaz/ui` 三段：引擎参数、界面参数）、`persist.txt`（`ui-persist`：窗口位置、上次引擎等）、`save\saveBoardConfig.txt`；配置损坏时自动备份为 `config_wrong.txt` 并重建（`Config.java:917-929`）。持有数百个 UI 开关字段；默认引擎命令示例 `katago.exe gtp -model ... -config ...`（`Config.java:67-71`）、闪电分析默认命令 `katago analysis -model model.bin.gz -config analysis.cfg -quit-without-waiting`（`Config.java:436`）。
- **`ExtraMode.java`**：额外模式标记（9 行）。

### 3.2 `analysis` 包 —— 引擎层（22 个类）

**核心**

- **`Leelaz.java`（3689 行）**：单引擎 GTP 会话核心。`ProcessBuilder` 或 SSH 启动引擎；支持 `encryption||` 前缀的 AES 加密引擎命令（`Leelaz.java:251-272`）；两条常驻线程读 stdout/stderr；握手后按 `name` 响应识别 KataGo / KataGoPda(定制版) / ZenGTP / SAI / Sayuri / LeelaZero / Leela 0.11 / Pachi / KataJigo / Golaxy；按引擎类型拼装分析命令（`kata-analyze`、`lz-analyze`、`analyze`、`heatmap`）与对局命令（`kata-genmove_analyze`、`lz-genmove_analyze`、`genmove`），KataGo 额外携带 `ownership`/`pvVisits`/`movesOwnership` 标签；解析候选点行→`MoveData`；`kata-raw-nn N`（随机对称）实现热力图；支持双引擎模式下 kata-/lz- 前缀互转镜像。
- **`EngineManager.java`（2314 行）**：引擎清单与对局编排。全量重建/预载引擎列表、切换引擎（处理棋盘尺寸/komi/缓存）、每 5 秒检查死进程自动重启；引擎 PK（分析模式双侧 ponder 或 genmove 模式配 `time_settings`）；多盘对局统计 Elo/标准差写入 txt；SGF/PNG 自动存盘。

**辅助引擎**

- **`AnalysisEngine.java`（437 行）**：KataGo `kata analyze`（JSON 分析模式）批量/闪电分析：遍历棋谱树逐节点发 `{"id","moves","analyzeTurns",...,"rules","komi","overrideSettings"}` 请求，解析 `moveInfos`/`ownership` 回填棋谱树。
- **`KataEstimate.java`（639 行）**：形势判断：KataGo 用 `kata-set-rules`+`kata-raw-nn 0` 取 ownership；Zen 用 `territory` 命令；结果交给棋盘渲染点目图与 `EstimateResults` 窗口。
- **`ContributeEngine.java`（1160 行）**：可视化 KataGo 分布式训练：`<katago> contribute -override-config "serverUrl=https://katagotraining.org/,username=…,password=…,logGamesAsJson=true"`（`ContributeEngine.java:79-101`），解析 stdout 的 JSON 对局流实时同步到棋盘（按 gameId 处理乱序补包），支持暂停/恢复。
- **`CaptureTsumeGo.java`（266 行）**：启动捆绑 jar `captureTsumeGo\CaptureTsumeGo1.2.jar` 做死活题截屏识别，行协议回传棋盘矩阵写入 `Board`。

**外部进程桥**

- **`ReadBoard.java`（841 行）+ `ReadBoardStream.java`**：棋盘同步。Windows 版走 `readboard\readboard.exe`（命名管道）或 `.bat`+本地 socket；Java 版走捆绑的 `readboard_java\readboard-1.6.2-shaded.jar`；行协议 `re=<棋盘矩阵>`、`sync/both/noponder/inboard/play`（自动落子“溜狗”调用 `leelaz.genmove`）。
- **`GetFoxRequest.java`（113 行）**：野狐棋谱下载桥，启动捆绑闭源 `foxReq\FoxRequest.jar`（UTF-8 行协议），结果回传 `FoxKifuDownload`；fox 接口实现在闭源 jar 内，不在本仓库。
- **`FastLink.java`**：通用 `ProcessBuilder` 启动用户自定义命令。

**数据与 SSH**

- **`MoveData.java`（538 行）**：单手候选数据及 6 套解析器（LZ 整数胜率 / KataGo 小数+pvVisits+movesOwnership / SAI / 各 summary 正则 / Zen）。
- **`Branch.java`（167 行）**：把 PV 变化串推演成 `BoardData` 快照供渲染。
- **`SSHController` 等 4 个控制器**：ganymed-ssh2 远程引擎；密码经 `Utils.doDecrypt` 解密或公钥认证；`RemoteConnect` 解析 `ip[:port]`（默认 22）。
- **`GameInfo` / `EngineGameInfo` / `ContributeGameInfo` 等**：对局元信息与 PK 状态机 POJO。

### 3.4 `rules` 包 —— 棋规与棋谱（19 个类）

**棋盘数据模型**

- **`Board.java`（4523 行）**：棋盘规则核心。静态 `boardWidth/boardHeight`（默认 19，支持变长棋盘）；`place()` 加锁执行落子：四方向洪泛提子 + 自杀检测（`Board.java:2022-2123`）；用 Zobrist 哈希做简单劫判断（与上一节点比对，`BoardHistoryList.java:304-310`；全链 `violatesSuperko` 存在但从未被调用，属死代码）。另含棋盘编辑（死子标记）、数子（`ScoreResult`）、试下、插入/旋转/翻转棋谱、自动对弈落子等大量功能。
- **`BoardHistoryList.java` / `BoardHistoryNode.java` / `BoardData.java`**：带头指针的棋谱树——每节点持 `BoardData`（局面快照 + 引擎分析数据 bestMoves/胜率/目差 + SGF 属性 + 评论）与子变例表；`addOrGoto` 按子节点 Zobrist 相等实现"重放同型局面不删支"（`BoardHistoryNode.java:183-199`）。`BoardData` 属性用 `HashMap` 存储（丢失顺序与重复键，`BoardData.java:63`）。
- **`Zobrist.java`**：静态随机表 + 异或维护局面哈希，用于劫检测与变例去重。
- **`Stone.java`**：黑/白/空/黑河/白河/虚着枚举。

**棋谱读写**

- **`SGFParser.java`（3471 行）**：手写字符级状态机解析 SGF（FF4 子集：`B/W、C、AB/AW/AE、PB/PW/RE、KM、SZ`（含矩形棋盘）、标记类属性 `LB/CR/SQ/MA/TR`；兼容长格式小写标签）。**私有扩展**：`LZ/LZ2/LZOP/LZOP2`（Lizzie 系引擎分析缓存随棋谱保存/回填）、`DZ`、`DD[true]`、`FIT`；≥52 路棋盘用非标准 `x_y` 坐标；保存时写 `CA[UTF-8]` 并可把每手的胜率/计算量/点评写入注释（`appendGameTimeAndPlayouts`、`formatComment` 系列）。编码用 juniversalchardet 探测。
- **`GIBParser.java`（126 行）**：Tygem `.gib` 格式（`INI/STO/SKI` 行、`GONGJE:` 贴目、9 种让子摆位）；仅当扩展名为 `.gib` 时由 `LizzieFrame.loadFile` 调用（`LizzieFrame.java:3545-3546`）。不支持 NGF/KIFU 等其他格式。

## 5. 结论

LizzieYzy 是一个功能密度很高的 Lizzie 深度 fork：以 KataGo 为主力的实时分析、闪电/批量分析、鹰眼复盘、引擎对局、形势判断、死活题框架、双引擎对比等核心功能链路完整（引擎层 → 规则层 → 渲染层的数据流清晰），对 KataGo 新版协议（ownership/pvVisits/movesOwnership、analysis JSON 模式、WRN/PDA）的适配在写作当时相当到位。

但从 yzy2.5.3（约 2023-06）之后项目不再活跃，代码呈现明显的"单作者快速迭代"特征：

1. **自建云服务整体下线**：`lizzieyzy.cn` 五个端口支撑的分享/检索/更新检查全部失效，是确定性"过时功能"中影响最大的一块；
2. **在线直播同步依赖逆向私有协议**（野狐、弈客），属于"随时会坏"的功能；JCEF Chromium 95 进一步放大了浏览器相关功能的脆弱性；
3. **旧引擎兼容代码（LeelaZero/Leela/Zen/SAI/Pachi/Sayuri）成为历史包袱**，实际使用价值取决于用户自行找到旧引擎二进制；
4. **并发安全与资源管理问题较多**（非 EDT UI 操作、进程判空、流泄漏），在特定场景（引擎 PK、SSH 引擎、中文 Windows 编码）会触发真实故障；
5. **安全设计薄弱**：硬编码 AES 密钥、明文凭据落盘/进命令行/走明文 TCP。

如果要在今天继续使用/维护它：核心本地分析功能（KataGo + SGF + 鹰眼 + 批量分析）依然可用且有价值；建议首先摘除或隔离 §4.1 的死服务调用（避免启动期无谓的连接超时），再把引擎流编码统一为 UTF-8、修复 §4.3 中标出的引擎 PK/SSH 相关 NPE 与线程问题。
